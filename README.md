# OpenCV + Dobot 机械臂手眼标定与抓取

用摄像头拍桌上的 A4 标定纸（四角各一个二维码），算出「像素坐标 → 机械臂坐标」
的映射矩阵，然后把纸面上任意一点换算成机械臂能走到的位置，去抓方块。

对应《方案.md》的第三、五阶段。分成两层：

- **标定/验证层**（`step1`~`step4`）：**四步，一步一个脚本，顺序不能反** ——
  生成纸 → 对刀 → 算矩阵 → 验证。跑到这里，纸面上任意一点都能换算成机械臂坐标了。
- **应用层**（`color_vision` ⑦ → `deepseek_brain` ⑤ → `main` ⑥）：
  认出方块在哪 → 把一句中文变成抓放动作 → 真的去抓。这一层才需要标定层的产物。

先跑通标定层（它只用到机械臂和摄像头），再上应用层。

## 装依赖

**先跑自检，它会逐项告诉你缺什么、该敲哪条命令：**

```bash
python3 tools/check_env.py
```

想直接装也行：

```bash
pip install -r requirements.txt
```

**Dobot SDK 不用装** —— 它已经放在 `sdk/dobot/` 里跟着项目走，脚本按绝对路径加载，
不依赖当前工作目录。

### ★ 系统依赖：Qt5（新机器上最常见的失败点）

`sdk/dobot/libDobotDll.so` 是越疆官方的二进制，它**动态链接了 Qt5**：

```bash
ldd sdk/dobot/libDobotDll.so | grep 'not found'     # 缺什么一目了然
```

缺了会报 `cannot open shared object file`，**光把 .so 复制过去是没用的**。装：

```bash
sudo apt install libqt5serialport5 libqt5network5 libqt5core5a
```

### ★ 适用平台

这个 `.so` 是 **x86-64 Linux 专用 + Dobot Magician 型号专用**：

| 平台 | 能用吗 |
|---|---|
| x86-64 Linux（装了 Qt5） | ✅ |
| ARM（树莓派）、Mac、Windows | ❌ 二进制架构/格式不对，得换越疆对应平台的 SDK |
| 越疆其它型号（如 MG400、CR 系列） | ❌ 指令集不同，得换对应 SDK |

换成别的平台的 SDK 时，把 `sdk/dobot/` 里的两个文件替换掉即可，
或用 `export DOBOT_SDK_DIR=/path/to/run-linux` 另指一份，代码不用改。

### 不用改任何路径

- SDK：项目自带 `sdk/dobot/`，加载逻辑在 `src/dobot_sdk.py`
- 串口：自动找（`--port` 可手动指定）
- 摄像头：按设备名自动挑外接的（`--cam N` 可手动指定 `/dev/videoN`）
- 文件路径：全部集中在 `src/paths.py`

```bash
# ⓪ 先回零（新机器/断电重上电/丢步报警后必做）

#   ★ 会大幅运动，清空周围 60cm。有 8 秒倒计时可 Ctrl-C 中止

# ① 生成标定纸（已经有了 data/ 就跳过）
python3 src/step1_gen_paper.py
#   打印 data/calib_A4_qr.png —— 必须 100% 比例，不能「适应页面」
#   ★ 只在你**从零开始**时才这么走。本项目现在的 json 是拿卷尺量手上那张纸
#     重建的（meta.source=measured-sheet），**和这个 PNG 不配套** ——
#     沿用手上那张纸就行，别重印。而且 step1 会**拒绝**覆盖那份实测 json。
#     详见下面「先看清 json 和 PNG 是不是同一张纸」。

# ② 手动对刀：依次把吸盘中心对准四个码的参考点，按 q 存盘
python3 src/step2_teach_coords.py --reference corner_tr
#   ⚠ 只有按 q 才会存盘；Ctrl-C 退出不存

# ③ 自动标定：摄像头拍纸 → 解四码 → 拟合矩阵
python3 src/step3_hand_eye_calib.py

# ④ 验证：看某个纸面点在两套映射下的预测，或连臂悬停比对
python3 src/step4_pick_test.py --at P4.tr          # 只看账，不连臂
python3 src/step4_pick_test.py --probe             # 连臂触底量纸面 Z
python3 src/step4_pick_test.py --at P4.tr --go     # 连臂悬停，人工看准不准
```

### 参考点约定（最容易搞错的一处）

「参考点」= 二维码**黑色图案**的右上角 = 数据区右上角。**不是**含白边的外框角
（两者差 4 个模块 ≈ 5mm，肉眼看不出，量错了标定残差也查不出来）。

step2 和 step3 的 `--reference` **必须一致**，两边默认都是 `corner_tr`。
不一致时 step3 会拒绝出矩阵并提示。

## 接入 DeepSeek（⑤ 决策）

把「方块在哪」+「用户一句话」变成「抓哪、放哪」的 JSON。**这一段不碰摄像头、
不碰机械臂**，所以底座还没做好也能先跑通、先验证 —— 方案里也是这么排的
（Day 3：脱离机械臂，只写请求 API 的代码）。

```bash
export DEEPSEEK_API_KEY='sk-...'          # 必须走环境变量，绝不要写进任何文件
python3 src/deepseek_brain.py --dry-run   # 只打印要发出去的 prompt，不联网、不花钱
python3 src/deepseek_brain.py --selftest  # 离线自检（换算规则/解析/比对），不联网
python3 src/deepseek_brain.py --demo      # 用虚拟坐标跑用例，逐条和标准答案比对
python3 src/deepseek_brain.py --demo --repeat 5    # 稳定性检验（成倍花 tokens）
python3 src/deepseek_brain.py --say "把绿色方块放到红色方块右侧"
```

接口（主程序将来就按这个接）：

```
world_state（OpenCV 写） + 一句中文
        ↓                          ↑ 抓取点 = 方块现在在哪
   [{"obj", "grasp": {x,y,z_level}, "place": {x,y,z_level}}, ...]
                                     ↓ 放置点 = 按指令算出来的目标位置
```

**只用标准库 `urllib`，`requirements.txt` 不用加东西。**

### 真坐标从哪来：不用改这个文件

`src/deepseek_brain.py` 里的 `VIRTUAL_WORLD_STATE` 是占位的假坐标，只为了让决策
链路能跑起来（它和方案第 64-71 行的 `world_state` 同形）。**它已经不再是唯一的
来源了** —— `src/color_vision.py`（⑦）现在会真的从相机认出方块、写成
`output/world_state.json`，`main.py` 默认就读那份（优先级见下面「跑主程序」一节）。
决策层这个函数拿到的一直是同一个形状的字典，**换成谁给的都不用改一行**。

真要用它兜底只有一种场合：底座/相机都还没接好，想先跑通链路 ——
那时用 `main.py --virtual`。它可以，但**结果不会写进记忆库**。

### 关于模型名

方案里写的「DeepSeek v4.1」**不存在**。实际可用的只有两个（`GET https://api.deepseek.com/models`
查到的）：`deepseek-flash` 和 `deepseek-v4-pro`。两个都是**推理模型**，返回里带
`reasoning_content`（用 `--show-reasoning` 能看），会体现在延迟和 tokens 上。

### 模型选择

**默认用 `deepseek-flash`。** 同一套 8 个用例跑下来的实测：

| | `deepseek-flash` | `deepseek-v4-pro` |
|---|---|---|
| 正确率 | 39/40 | 40/40 |
| 单次耗时 | 2.42 s | 3.23 s |
| tokens（8 用例一轮，5 轮均值） | 9221 | 9228 |

**注意 tokens 两边基本一模一样**（差 0%）。两个都是推理模型，推理长度相当，
所以 flash 省的是**时间**（约快 25%），不是 tokens。别以为换 flash 就省钱 ——
除非单价不同，那以官网价目为准。

#### flash 的唯一毛病：偶尔漏掉最外层的方括号

单动作的指令（比如「把红色方块放到黄色方块上面」），flash 偶尔会把结果返回成
**裸对象** `{...}`，而不是协议要求的 `[{...}]`（v4-pro 没见过）。**它算得是对的，
只是少写了一对方括号。** 这会让主程序直接判为无效。

针对它做了**两层**，缺一不可：

1. **源头（prompt）**：`build_messages()` 里加了一条硬规则「最外层永远是方括号，
   没有例外」，外加两组带方括号的**格式示例**（单动作 + 多动作各一个）。
2. **兜底（解析器）**：`parse_actions()` 遇到裸对象会包成单元素数组 —— 意思唯一确定，
   属于还原不属于猜。字段照样逐个校验，残缺的对象仍然被拒。
   `--selftest` 里有专门两条覆盖（还原 + 畸形仍报错）。

A/B 实测（直接看**原始返回**的首字符，绕过解析器，同口径各 36 次）：

| | 打滑率 |
|---|---|
| 旧 prompt | 6.8%（3/44） |
| 新 prompt | **0%（0/72）** |

⚠️ **这个对比说明不了太多**：单侧 Fisher p ≈ 0.052，卡在 0.05 线上，属于「有迹象
但没到统计显著」。要压到 p<0.01，新 prompt 得测到约 180 次无打滑。所以别把
「prompt 治好了」当成结论 —— **真正保证不出事的是第 2 层那个解析器兜底**，
prompt 只是让它少发作。

有一点可以确定：**flash 打滑时错的是括号，不是「把方块放到反方向」**。
后者才是真错，而那种错两个模型都没出过。

要换回 v4-pro：命令行加 `--model deepseek-v4-pro`，或改 `src/deepseek_brain.py`
里的 `DEFAULT_MODEL` 一行。

### ★ 唯一用虚拟坐标验不了的事

`SIDE_OFFSET_MM`（左右前后到底该加减 X 还是 Y）抄自方案第 84 行，
**还没在真机上验证过**。虚拟坐标下方向反了也一切正常、不报错、测试全绿 ——
等接上真机械臂才会发现方块放到反方向去了。

所以接上真机械臂后：**只放两个方块、只走一次，人眼看一眼方向**，确认了再往下跑。
真错了就只改 `SIDE_OFFSET_MM` 那一张表，**不要去改 prompt 里的文字描述**
（那一处是接口，改了会和校验层对不上）。

## 跑主程序（⑥ 一句话 → 机械臂抓放）

`src/main.py` 是**最终入口**：把前面几段串起来。

```
color_vision.py 认出方块在哪 ─┐
（⑦ 输出 output/world_state.json）│
                    ├→ DeepSeek（⑤）→ 动作 JSON ─→ main.py（⑥）→ 机械臂
用户说的一句话 ──────┘                            算出该降到哪、该走哪条路
                                                  跑完再把结果写回 world_state.json
```

它自己**不做识别**，只吃「方块坐标字典 + 一句话」。这个字典的优先级是
`--world-json 文件` > `output/world_state.json`（记忆库，**默认**）> `--virtual`（编的假坐标）。
来源每次都会打印在 `[坐标来源]` 那一行 —— **先看那一行**，就知道这份计划值不值得信。

### ⑦ 让摄像头认出方块：`color_vision.py`

```bash
python3 src/color_vision.py --camera --debug   # 连摄像头识别，出一张调试图
python3 src/color_vision.py --image 照片.jpg --paper-mm   # 拿一张照片离线跑，不连臂不用标定
python3 src/color_vision.py --selftest         # 离线自检：合成一张标定纸 + 四个色块，全自动
```

**不要"训练"识别颜色。** 纯色方块的识别是 HSV 阈值 + `cv2.findContours`，
《方案.md》第 60-61 行就是这个思路。阈值是白纸黑字的数字、可以直接看、可以直接改；
训练出来的模型反而说不清为什么认错。所以：

- 认不出某个颜色 → 跑 `--debug`，看 `output/color_debug.png` 上哪个颜色的框没套上，
  改 `src/color_vision.py` 开头的 `HSV_RANGES`（那里写了怎么调）。
- 红色要**两段** H 区间（0-10 和 170-180）：OpenCV 的 H 是 0~179，红跨在接缝上，
  只写一边必然漏。`--selftest` 里有专门一条钉这个。
- 认不出来时它会**拒绝出结果**并报「本帧只认到 […]」，
  所以「相机没拍到」和「阈值偏了」一眼能分开。

#### ★ 标定纸还没做好时：`--hsv`（唯一不需要二维码的用法）

```bash
python3 src/color_vision.py --camera --hsv            # 方块 + 摄像头，就这两样
python3 src/color_vision.py --image 照片.jpg --hsv    # 手机拍的也行
```

它**只实测 HSV、不算坐标** —— 不读 `data/calib_A4_qr.json`、不要标定矩阵、
不要机械臂、不要二维码。这是上面那条「阈值要按你的方块和你的灯来调」的落地工具，
而且调阈值这件事和二维码**一点关系都没有**，不该被「纸还没做好」挡住。

它逐色报出：掩膜多少像素、最大那块多大/什么形状/共几块，以及那块里 H / S / V 的
p5 / p50 / p95 —— **同一个量给两列**：

| 列 | 是什么 | 能回答什么 |
|---|---|---|
| **现配置** | 按 `HSV_RANGES` 现在这套阈值切出来的掩膜里量到的 | 掩膜干不干净、方块认不认得出来 |
| **放宽后** | 把 H 两边各放宽 10、S/V 下限降到 40 重新切一遍再量 | **配置有没有切边** |

> ★ 「现配置」那一列**不能单独看**，这是个坑：掩膜本来就是按配置切出来的，
> 区间外的像素压根不在里面 —— 所以它的 H 永远落在配置区间**内**、S/V 的 p5 永远
> ≥ 配置下限。**光看它，永远看不出「区间写窄了」**。实测过：一块 H 铺满 14~35 的
> 黄方块，配置写 20-35，它会报「p5 = +20」正好压在下界上、还显示「✅ 采用」，
> 而方块左边那一截其实一直在丢。
>
> 「放宽后」那列才可能跑到配置区间外面去 —— 跑出去了就是配置在切边，下面会
> **直接点出来**：`★ H 在切边: 放宽后实测 +15 ~ +34，配置只有 +20 ~ +35`。

「放宽后那块多 Npx」= 放宽后同一块涨了多少像素。几乎不涨 = 配置没切到实体
（那掩膜里的杂块就是**真的同色背景**，该反过来**收** H 区间）；涨一大截 = 一直在
丢方块边缘。★ 它只比**跟现配置那块连长在一起的那一块**，不算别的 —— 放宽 H 会把
邻色的东西也圈进来（green 放宽到 30-95 就吃掉了 H≈32 的橙黄），不筛的话这个数会报假警报。

`output/color_debug.png` 上半 = 原图 + 四色轮廓，下半 = 四个掩膜 **2x2**：

红色那一路会**自动把 170~180 折成负数**再报，否则百分位数会落在 5 和 175 之间，

> 形状（fill）和块数 —— 上面那个例子现在会被标成

`--paper-mm` 只报纸面毫米坐标，**不需要手眼矩阵** —— 底座还没好就能验证识别对不对。

### ★ 记忆库：相机看不出「摞了几层」

`output/world_state.json` 不只是缓存，它是**有状态的**，这一点最反直觉：

- 相机能给的是 **x/y**；
- **z_level（摞在第几层）相机永远看不出来** —— 俯拍图上摞在第二层的方块和躺在
  地上的长得一模一样。

所以 z_level 只能「这条指令执行完之后改一次」一路记下来（《方案.md》第五阶段
「刷新记忆库」）。`main.py --go` 跑完会：

1. 只把**真的关过真空、方块已落桌**的那些动作写回 `world_state.json`
   （跑挂时"已经放好的那几个"照样要记，不然下次对着空地抓）；
2. 中止时吸盘上还吸着的那块，位置已不可知 → **从记忆库里删掉**，
   而不是留着一个错的位置骗下一条指令；
3. 覆盖前把上一份留成 `.json.bak`。

写进去的层数用的是**决策层算出的「放完之后在第几层」**，不是简单的「旧层 + 1」。
这两种写法在「摞上去」时一样，在「放到旁边」时**完全不同**：放到桌上层数是 0，
而旧层 + 1 会记成 1 —— 下一轮叠放就会多降一个方块的高度。自检里专门钉了这一条。

### ★ 每条记录还有两个「戳」：`src`（谁给的坐标）和 `half`（在纸的哪半边）

相机写进去的每条记录多带两个键，它们**不参与任何坐标计算**，只决定
「第一次抓取要不要补偿 5mm」：

- `"src": "camera"` = 「这条 x/y 是相机刚拍的、机械臂**还没碰过**这块方块」；
  没有这个键 = 机械臂已经动过它，按真实值走。
- `"half": "left"` / `"right"` = 「这块在**纸的哪半边**」（`left` = P1/P3 那一侧，
  `right` = P2/P4 那一侧）。判不出来（四个二维码没解齐、拟合不出像素↔纸面）
  **就不写这个键** —— 判不出来就不补偿，不猜。

**第一抓要补偿 5mm —— 两半边补的方向不一样。** 实测发现，方块坐标刚被相机刷新过时，
第一次抓取吸盘落点和检测位置偏了一点点；同一块方块再抓第二次就准了。偏法**左右两半
不同**（用户分别报的），所以 `main.FIRST_GRASP_OFFSET_MM` 是一张**按半侧查的表**：

| 半侧（`half`） | 补什么 | 表里的值 | 为什么 |
|---|---|---|---|
| `left`（P1/P3 那侧） | 往机械臂**右边**挪 5mm | `(0, -5)` | 第一抓总偏左 → Y 减 5 |
| `right`（P2/P4 那侧） | **X 比实测值大** 5mm | `(+5, 0)` | 第一抓 X 差 5mm |

记号沿用全项目那一条：**右 = Y −**（见 `deepseek_brain.SIDE_OFFSET_MM` 的注释）。
两个数说的都是**机械臂坐标**，正负直接照机械臂来。

> `half` 是在**纸自己的坐标系**里判的（`paper x < 纸宽/2`），不是拿机械臂坐标猜。
> 纸被挪了、机位被撞了，纸面的左右分界线都不变；拿机械臂坐标划线的话，下次
> 重架摄像头就得重新量一个阈值。

计划打印里会单独写一行「相机给 (…) → 实际去 (…)」并点名是**哪半边**，所以计划上的
数字和识别结果对不上是**故意的**。没补的两种情况（判不出半侧 / 机械臂碰过了）不会
打印这一行 —— 它们都是「就该这样」。

**戳只在第一次有效**，因为这块方块一旦被抓过，`refresh_world_state` 会把它那条
**整条重写**成机械臂确认过的坐标（新记录两个键都没有）—— 之后一律按真实值走，
5mm 不会一次次叠加。`world_state.json` 里那些没带 `src` 的记录（比如
`--world-json` 手写的、或已经被机械臂动过的）永远不补这 5mm。

改表里的数之前先确认方向：左半边想要「更靠右」就是 dy 为**负**（缩成 0 或正数都是
反方向/不补）；右半边说的就是 X，+5 是「比实测值大」。半侧判不出来时表里查不到 →
不补，不拿默认值赌方向。

### ★ 「放到某块旁边」的中心距是 50mm（不是方块边长 30mm）

`deepseek_brain.SIDE_GAP_MM = 50`。自然语言说「放到红色方块右侧」而**没给距离**时，
落点与红色方块**中心**相距 50mm。

为什么不是 30mm（= 方块边长）：中心距等于边长时两块**面贴面**，一点缝都没有 ——
相机有误差、机械臂有误差，任何一点偏差就直接撞上去。50mm 留了 20mm 缝。

- 这个数只影响**摆放间距**；方块**物理尺寸**仍是 `CUBE_MM = 30`（抓取高度、
  叠放高度、避障高度全靠它）。两者是两件事，别再合回去。
- 它进了 `rules_fingerprint()`。所以间距一改，`output/last_plan.json` 里那份旧计划
  会被自动判为「不能复用」并重问 DeepSeek —— 旧计划的 place 坐标看起来完全合法
  （就是老间距那个值），不拦就会照 30mm 摆、两块贴在一起。
- prompt 里那句「中心相距 50mm」和四个方向的具体数字都是**从这张表生成的**，
  不手写。改 `SIDE_GAP_MM` 一处，prompt、自检、指纹三处一起跟着变。
- 这条规矩管的是「**没说距离**」的默认值。指令里额外说了别的距离时，模型怎么理解
  没有保证 —— 那属于新需求，别指望它自动生效。

于是有几条硬规矩：

- **手工挪过方块就必须 `--reset-world`**（删掉记忆库，层数从 0 重来），
  否则记忆里的位置/层数和眼前的桌面对不上。
- 用 `--virtual`（假坐标）跑的时候**不会写记忆库** —— 编的坐标写进去，
  下一条指令会把它当成"上次相机看到的"。
- 想从零开始：`--reset-world`。

一条指令的完整节奏（也是《方案.md》第五阶段第 4 条说的「系统待命」）：

```bash
python3 src/color_vision.py --camera      # ① 看桌面 → 刷新 x/y（z_level 沿用记忆库）
python3 src/main.py "把绿色方块放到红色方块上面"        # ② 只出计划，人过目
python3 src/main.py "把绿色方块放到红色方块上面" --go   # ③ 跑（跑完自动刷新记忆库）
```

要是想**连着做好几步**，别每次退回 shell 重敲一遍参数 —— 开一次交互模式：

```bash
python3 src/main.py -i --go        # 之后一行一条指令，参数只给这一次
```

```text
指令> 把红色方块放到绿色方块右侧          ← 打计划 → 按回车确认 → 动臂
指令> 把黄色方块摞到蓝色方块上面          ← 再来一条，不用重开命令
指令> quit                                ← 结束
```

### ★ 一次说好几步 / 交互模式

两条路，按你当时顺不顺手挑：

| 写法 | 什么时候用 |
|---|---|
| **一句话里带好几步** | 步骤你是**事先想好**的：`"把红色方块放到绿色方块右侧，再把黄色方块摞到蓝色方块上面"` |
| **`-i` 交互模式** | 步骤要**看着眼前结果**一步步定**：开一次命令，一行一条指令，`quit` 退出 |

两种都不用重敲参数。交互模式还省掉了引号 —— 一行就是一句中文。

★ **安全闸口一个都没少。** 交互模式缩短的只是**打字**，不是**确认**：
每条指令照样走完整流程（拿坐标 → 决策 → 规划 → 预检），给了 `--go` 时
**仍然在 TTY 里等你按一次回车才动臂**。一条指令失败（缺参数、够不着、预检没过）
只废掉那一条，循环接着读下一行；只有 Ctrl-C 会真的终止（中途停臂必须能停）。

★ `--reset-world` 在交互模式里**只在第一条指令生效一次** —— 否则第二条会把
第一条刚写进记忆库的结果又删了（看上去就是「刚放好，下一句却说方块不存在」）。

★ 不给指令直接跑 `python3 src/main.py` 也会进交互模式；
但**管道/重定向里不行**（它要一行一行读），那种情况会明确拒绝并提示你
把指令写在命令行上。

### ★ 默认不动臂，这是故意的

```bash
# 只出计划，机械臂一步都不动（默认）
python3 src/main.py "把绿色方块放到红色方块右侧"

# 看过计划、确认坐标对了，才真动
python3 src/main.py "把绿色方块放到红色方块右侧" --go
```

`--go` **默认执行的不是你刚说的话，而是上一次存进 `output/last_plan.json` 的那份
计划**。原因：DeepSeek 是推理模型、有随机性，同句话重问可能算出不同坐标 ——
那就等于「你过目的是 A，跑的是 B」。存盘 + 复用才能保证
**你看到的就是要跑的**。要重新问就加 `--fresh`。

真动臂还有两道闸：预检有问题直接拒绝；不在**交互式终端**里也拒绝
（要的就是你能 Ctrl-C）。跑之前它会要你按回车确认。

### 动臂前必须先知道「纸面 Z」

`main.py` 算不出吸盘该降到哪，除非知道纸面在哪。两个办法：

```bash
python3 src/step4_pick_test.py --probe        # 连臂触底量一次，存进 output/
python3 src/main.py "指令" --table-z -33.8    # 或者这次临时给一个
```

两个都没有时它会**明确拒绝并告诉你怎么办**，不会瞎猜一个 Z 去撞纸。

### 要叠放就必须量「净高」

第 0 层（直接放桌面）的算式和 step4 真机验证过的**逐位相同**，不用管这件事。
但要**摞到方块上**（`z_level ≥ 1`），就得知道方块的净高：

```bash
python3 src/main.py "把红色方块放到黄色方块上面" --table-z -33.8
```

`--net-h` **默认写死 25**（`main.DEFAULT_NET_H`，用户 2026-09-19 要求：
「不要让我每次都敲一遍」，所以上面这条命令不用再带它）。只在两种时候用得上：

1. 要**叠放**（`z_level ≥ 1`）；
2. 搬运**路径会经过**摞着的方块（要算它顶面多高）。

★ 这个 25 是个**假设** —— 假设方块真实净高就是 25mm。它**不是**拿 `--obj-h` 顶替的
（那样是错的，见下）。所以**卡尺量出来不是 25 就显式给**：

```bash
python3 src/main.py "把红色方块放到黄色方块上面" --net-h 24.2
```

显式给的数照旧压过默认值。为什么这件事不能糊弄（这是全项目最隐蔽的一处）：
`--obj-h`（默认 26）是「吸盘接触面到已记纸面 Z 的距离」，里面含了 **1mm 的吸盘唇口
压缩量** —— 那 1mm 只在你压到**最上面那一层**时才存在。叠第 2 层时真实增加的高度
是方块的**净高**（约 25）。照 26 叠会每层多算 1mm → 吸盘差 1mm 吸空，
而**这 1mm 从读数上完全看不出来**（`--obj-h 26` 在单层时是对的）。

★ 代码里 `nozzle_z` / `cube_top_z` 这两个库函数在 `net_h=None` 时**仍然拒绝**
（自检里钉着）—— 写死的只是**命令行默认值**，不是把"没量净高"这件事放行。

所以叠放前还是**用卡尺量一个方块的净高**。step4:476-499 的注释记过这件事的原始来龙去脉。

### ★ 搬运高度：平放的方块只留 20mm，近底座那一圈要提前降

吸着方块横着走时的高度不是常数，它由**路径上要越过的那块方块**决定：

```
搬运高度 = 那块方块的顶面 + 净空 + 被吸方块自身的厚度
```

**净空分两档**（`main.CARRY_CLEAR_LOW_MM` / `DEFAULT_CARRY_CLEAR`）：

| 要越过的是 | 净空 | 为什么 |
|---|---|---|
| **平放**的（第 0 层） | **20mm** | 只有一层高，从上面过要的净空本来就少 |
| **摞起来**的（≥1 层） | **35mm** | 顶上没有"平放"这个退路，宁可贵一点 |

分档的原因是 2026-09-19 的一次真机报警：桌上只有**一块平放**的方块横在路径上，
一刀切 35 把搬运高度顶到 `Z=67.51`，而这条路的降低点在**离底座只有 117mm** 处
—— 那个半径上机械臂最多只够到 `Z≈64.5`，于是"抬到一半停住、底座报警"。
分成两档后同一场景只要 `Z=52.51`，够得着了。

**近底座那一圈**（`main.NEAR_BASE_R_MM = 150`）：越靠近底座，同一个半径上能抬到的
高度越低（实测: 151.7mm 随便走，130mm 时 Z=94.51 走到一半停住，117.5mm 时 Z 只到
约 64.5）。所以计划会在**踏进这一圈之前**就把高度降下来，剩下的路低着走
（`early_descent`）。能不能在那儿降有两个条件：那一点周围 ≥ `NEAR_CLEAR_MM = 50mm`
没有别的方块（方块 30mm 见方，等于边上留 10mm 缝），且从那儿到落点一路干净。

> ⚠️ 这两个半径数**不是关节限位** —— SDK 里既没有逆解也没有限位可查
> （见 `main.execute` 里 `joints_note` 的说明）。它们只是照实测画出来的
> "该开始小心"的线。真遇到报警，把现场打印的**离底座多少 mm + J2/J3 角度**
> 记下来，才是下一次该往哪儿改路线的依据。

计划打印里这几行就是给这个用的（`搬运` / `升高点` / `降低点`），
撞了东西或者报警时先看它们。

  （不 `SystemExit`，否则会带走整场交互）、交互循环的空行忽略/坏指令不带走整场/
  `quit` 收工/`--reset-world` 只清一次、`-i` 后面带的那句先跑（不被静默丢掉）、
  以及非 TTY 环境明确拒绝。
  ★ 为此把命令行解析器抽成了 `build_argparser()` —— 之前它藏在 `main()` 肚子里，
  自检根本够不着「默认值到底是多少」这笔账。
- **⚠ 还没在真机上跑过。** 决策层（⑤）已经在真 API 上验证过，运动层的每一块
  （连接/报警/限位/真空时序）也都在 step2/step4 真机跑过，
  但**主程序这条完整链路一次都没连过臂**。第一次跑请：
  只放两个方块、只走一次、手放在电源旁边。
- 还有个只能靠眼睛验的东西（`SIDE_OFFSET_MM` 的方向），见上面那节。

### 常用参数

| 参数 | 作用 |
|---|---|
| `--table-z` | 纸面 Z。不给就找 `output/pick_test_result.json` |
| `--net-h` | 方块**净高**，**默认 25**（写死在 `main.DEFAULT_NET_H`）；量出来不是 25 就显式给 |
| `-i` / `--interactive` | 交互模式：开一次命令，一行一条指令（`quit` 退出） |
| `--obj-h` | 吸盘接触面到纸面的距离，默认 26（对齐 step4） |
| `--press` | 抓取时额外预压量，默认 0；放置永远不带 press |
| `--hover` | 悬停高度，默认 30 |
| `--world-json` | 从**指定文件**读方块坐标（不给则优先读 `output/world_state.json` 记忆库） |
| `--virtual` | 强制用项目自带的**虚拟坐标**跑链路；这些假坐标**不会**写进记忆库 |
| `--reset-world` | 删掉 `output/world_state.json`。**你手工重摆过方块就必须加这个** |
| `--mode` | `movl`（默认，直线）/ `movj` |
| `--fresh` | `--go` 时重新问一次 DeepSeek |
| `--clear-alarms` | 显式清限位类报警（丢步报警一律拒绝） |

## 交付给别人时：哪些给、哪些不给

### 对方拿到后的第一条命令

```bash
python3 tools/check_env.py
```

它会逐项检查 Python 版本、cv2/numpy/pillow、SDK 能否加载（= Qt5 齐不齐）、
串口权限、摄像头、中文字体、标定纸、`DEEPSEEK_API_KEY`（只报长度、不回显内容，
另做一次 TCP 连通性探测但不调接口），最后按 `output/` 里有什么告诉你**流程走到哪了、
下一步该敲哪条命令**。**缺哪项直接给出要敲的命令**。
有 `❌` 就返回码 1。全绿了再往下走。

（没设 API key 只算 `⚠ 建议`、不算 `❌`：step1~step4 全程不联网，对方该先能开始对刀。）

### ✅ 要给

| 文件 | 理由 |
|---|---|
| `README.md` | 上手说明 |
| `requirements.txt` | pip 依赖清单 |
| `docs/方案.md` | 设计背景 |
| `src/**` 全部 | 流水线代码 |
| `tools/**` 全部 | 排查工具（含回零） |
| `data/calib_A4_qr.json` | **必须给**：这是纸面几何，所有脚本的地基。没有它后面全跑不了 |
| `data/calib_A4_qr.png` | 给了对方才能重印这张纸 —— 但**只有当 json 是这张 PNG 排出来的才配套** |
| `sdk/dobot/**` | **必须给**：机械臂 SDK。给了对方才开箱即用，否则他要自己去越疆官网下 |

#### ★ 先看清 json 和 PNG 是不是同一张纸

`data/calib_A4_qr.json` 的 `meta.source` 有两种值，**决定 PNG 还有没有用**：

| `meta.source` | 含义 | PNG 配不配套 |
|---|---|---|
| `step1_gen_paper` | json 和 PNG 由 step1 一起排出来 | ✅ 配套，PNG 印出来就是这张纸 |
| `measured-sheet` | json 来自 `tools/make_layout_from_sheet.py`，是**拿卷尺量你手上那张纸**重建的 | ❌ **不配套**，PNG 只是早期的排版模板 |

本项目的 json 现在是 **`measured-sheet`**（`qr_size_mm_actual` 35.905，
是按 29/21 从 26.0 外推出来的含白边边长）。也就是说：
**真实有效的是 json，PNG 只是模板** —— 拿这份 PNG 去打印，打出来的纸和 json 对不上。

所以交付时要说清一句：**让对方沿用手上那张（被测过的）纸**，不要重印 PNG。
真要换纸，就「先有纸，再量纸，json 跟着纸」，**不能反过来拿 json 去印纸**：

```bash
python3 tools/measure_guide.py        # ① 出一张图，告诉你新纸该量哪 6 个距离
                                      #    （会出到 output/measure_guide.png）
python3 tools/make_layout_from_sheet.py --paper 297 210 --side 26 \
        --ab 213 --cd 214 --ac 131 --bd 131 --ad 251 --bc 251
                                      # ② 把量到的毫米数填进去 → 重建 json
                                      #    （上面这组就是本项目当初量到的值）
python3 tools/check_env.py            # ③ 复查：应显示 标定纸来源: 按卷尺实测重建
```

`make_layout_from_sheet.py --help` 有每个参数的说明；`--side` 量的是**黑色图案
（数据区，21 模块）**的边长，不是含白边的整边长 —— 这两个差了 8 个模块，
是全项目最容易混的一对尺寸。

（`step3_hand_eye_calib.py:381-384` 的 `_warp_paper` 注释记过这件事：
标定自检里借 PNG 只是「造一张有四个码的图」，真值一律来自 json，所以自检不受影响。）

### ❌ 不要给（`output/` 整个目录）

`output/` 里全是**跑出来的产物**，而且每一项都**绑死了你这一台机器**：

| 文件 | 为什么不能给 |
|---|---|
| `output/hand_eye_matrix.json` | 手眼矩阵 = 你这台机械臂 + 你这个摄像头机位的绑定关系。对方机位不同，拿去用会**算错坐标还不报错**，是全项目最危险的一个文件 |
| `output/robot_points.json` | 你测的四个教点，只在你的底座高度下成立 |
| `output/pick_test_result.json` | 你实测的纸面 Z，同上 |
| `output/last_plan.json` | 你上次那份计划，里面的坐标绑死你这台臂。而且它会让 `--go` 直接跑你的旧计划 —— 对方会一头雾水 |
| `output/world_state.json`（含 `.json.bak`） | 桌面**记忆库**：你这几个方块现在摆在哪、摞到第几层。对方桌面上摆的根本是另一组方块 —— 给他等于让他在**错误的坐标**上抓，而且**不报错**（和手眼矩阵同级危险，道理见上面「记忆库」一节） |
| `output/color_debug.png` | 你调 HSV 时的抓图，派生图 |
| `output/shots/` | 调试抓图，无意义 |
| `output/*.png`（两张图例） | 派生图，对方自己跑 `step1` / `tools/measure_guide.py` 就能出 |
| `__pycache__/` | 字节码，换环境自动重建 |

**打包前执行：**

```bash
rm -rf output/* __pycache__ src/__pycache__ tools/__pycache__ sdk/dobot/__pycache__
```

对方拿到后要**从头跑 `check_env` → 回零 → step2 → step3**，因为零位、教点和
矩阵都必须在他的机器上重测。他只跑 step3 会看到：

```
❌ DOBOT_COORDS 里这些还没填: ['P1', 'P2', 'P3', 'P4']
  推荐: python3 src/step2_teach_coords.py --reference corner_tr   # 交互式逐个对刀，自动落盘
```

即被明确指回 step2，**不会静默算错坐标**。这是刻意的：手眼矩阵绑死机器，
绝不允许拿着别人的矩阵凑合跑。

## 离线自检（不用接机械臂/摄像头）

改完代码或换机器后，先跑这几个确认环境没问题：

```bash
python3 src/deepseek_brain.py --selftest                # 决策层：换算规则/JSON 解析/比对
python3 src/main.py --selftest                          # 主程序：Z 算式/限位/真空时序/记忆库刷新（不联网）
python3 src/color_vision.py --selftest                  # 识别层：合成一张标定纸+四个色块，全自动
python3 src/step2_teach_coords.py --selftest            # 运动/限位/报警逻辑
python3 src/step3_hand_eye_calib.py --selftest          # 标定数学 + 角点约定
python3 src/step4_pick_test.py --selftest               # 映射对比 + 抓取高度
python3 tools/make_layout_from_sheet.py --selftest      # 纸面几何重建
python3 tools/measure_guide.py                          # 出量尺图（顺带验证 PIL/numpy）
```

`deepseek_brain` / `main` / `color_vision` 的 `--selftest` **都不联网、不连臂、
不用摄像头、不用标定** —— 改完代码先跑这几个。

`color_vision --selftest` 的做法值得说一句：它借 step1 的 `encode_qr_modules()`
（底层是 `cv2.QRCodeEncoder_create()`）**现画一张标定纸**，再往上贴四个纯色方块，
然后让整条识别链路去认。真值来自 `data/calib_A4_qr.json` 的布局定义，
不是从 PNG 图上量出来的 —— 所以它验的是「代码算得对不对」，
不受「你手上那张纸和模板像不像」影响。它还会特意把这张合成图
**加一次透视投影**再认一遍（模拟相机没架正），平视能过、斜着过不了的那种 bug
就是被这一步抓出来的。

`deepseek_brain --demo` 才真的调 API（要 key、花 tokens）。

### 卡住了也能干的活（按「缺什么」分）

| 缺的东西 | 还能做什么 | 命令 |
|---|---|---|
| **标定纸**（码/底座没做好） | 用**真方块 + 摄像头**把 HSV 阈值调准 —— 这是唯一不需要二维码的识别通路 | `python3 src/color_vision.py --camera --hsv` |
| **摄像头**（只有方块） | 手机拍一张照样能调阈值 —— `--hsv` 那条的通路本来就不需要实时画面 | `python3 src/color_vision.py --image 照片.jpg --hsv` |
| **机械臂**（但有摄像头） | 验识别准不准：照片里连四个码一起拍进去，报纸面毫米坐标（不要手眼矩阵） | `python3 src/color_vision.py --image 照片.jpg --paper-mm` |
| **DeepSeek key** | 决策层照跑（`--dry-run` 不联网、`--selftest` 纯离线） | `python3 src/deepseek_brain.py --selftest` |
| **摄像头且没机械臂** | 全链路离线自检（合成标定纸，图像是造出来的） | 上面那一整排 `--selftest` |

**唯独这些非等硬件不可**：step2 对刀（要吸盘对准纸上的码）、step3 标定（要四码同框）、
step4 的 `--probe` 量纸面 Z（要吸盘真的触底）、`main.py --go`（要动臂）。
这四件里，前两件只要有那张纸就能做，第三件要底座。

接上硬件后再跑（**新机器按这个顺序**）：

```bash
python3 tools/check_env.py            # ⓪ 环境自检（先跑这个）
python3 tools/dobot_check.py          # ① 只读体检：SDK 能不能加载 + 报警 + 回零原点
python3 tools/home_arm.py             # ② 回零（会大幅运动！清空周围）
python3 tools/qr_camera.py --list     # ③ 看摄像头认到没
python3 tools/test_camera_qr.py       # ④ 看四个码能不能同时看清
python3 src/color_vision.py --camera --debug   # ⑤ 看四个方块认不认得出
```

`dobot_check.py` 放在最前面是有意的：它**只读、不发运动指令**，能在机械臂动
之前就把「SDK 加载不了 / 有丢步报警 / 回零原点被改过」这类问题暴露出来。

## 常见坑

1. **按 `q` 才存盘。** `step2` 交互式对刀，Ctrl-C 退出**不存盘**。
2. **打印不能缩放。** 标定纸按 100% 打印；缩放会让纸面几何和 json 对不上。
3. **别瞄白边外框的角。** 参考点是黑色图案的右上角。
4. **换底座高度就要重测。** 换底座、相机挪位置、重新回零 —— 都要重跑 step2 + step3。
5. **丢步报警必须先回零。** 出现丢步报警后，所有坐标读数都不可信。
6. **合规报警时 step2 会拒绝动。** 上电自复位报警会自动清；限位等要显式加
   `--clear-alarms`；丢步报警**拒绝**清除。
7. **新机器上 `.so` 加载失败 = 缺 Qt5。** 见上面「系统依赖」。别以为是 SDK 文件没拷全。
8. **回零会大幅运动。** `tools/home_arm.py` 跑之前清空机械臂周围和上方 60cm。
   它**只发 SetHOMECmd，不碰 HOMEParams** —— 这是从「有人把回零原点写成
   (200,200,200,200) 导致全部坐标整体偏移」那次事故留下的规矩。要改回零原点
   请用 DobotStudio，别在脚本里顺手改。
9. **没插外接摄像头时，脚本会退回笔记本内置的。** 内置的对着人、拍不到桌面，
   标定必然失败，但报错会像是「二维码没凑齐」。`tools/check_env.py` 会直接
   点出来 —— 它检测的是「脚本自动挑中的那个是不是外接的」，不只是「有没有摄像头」。
10. **要叠放就必须量净高，别拿 `--obj-h` 凑。** `--obj-h`（26）含 1mm 吸盘压缩量，
    只在最上面那层成立。`--net-h` 现在**默认 25**（不用每次敲），但那是个**假设**：
    卡尺量出来不是 25 就必须显式给，否则每叠一层都差 (25 − 真实净高)。
    库函数在 `net_h=None` 时仍然拒绝 —— 写死的只是命令行默认值。
11. **`main.py --go` 跑的是上次存下的计划，不是刚打的那句话。** 想重新问就加
    `--fresh`。这条是为了保证「你过目的」和「实际跑的」是同一份。
12. **`main.py` 没在真机上跑过。** 决策和运动两段各自验过，但这条完整链路没有。
    第一次务必只放两个方块、只走一次、人盯着。
13. **手工挪过方块，就必须 `--reset-world`（或重跑 `color_vision.py --camera`）。**
    要记住 `output/world_state.json` 是**有状态的**：x/y 靠相机刷新，
    **`z_level` 只能靠「每条指令跑完刷新一次」一路记** —— 相机从上往下看，
    永远分不出方块是在桌上还是在另一个方块上。你手工重摆之后记忆没跟着变，
    下一次叠放就会按**错的层数**降吸盘，而且**不报错**。
14. **`main.py` 中途失败时，吸盘上那个方块会从记忆库里被删掉。**
    这不是丢数据，是故意的：它现在掉在哪、在第几层没人知道，
    留着旧位置反而会害下一次对着空地抓。看到那句 `⚠⚠` 就人工把它摆好、
    重跑一次 `color_vision.py --camera`。
15. **`--virtual` 的假坐标不会写进记忆库。** 它是给你「底座/相机还没接好时
    先跑通链路」用的，写进去等于把记忆库毁了。真机上别拿它当坐标源。
16. **交互模式（`-i`）里 `--go` 是开命令时定死的。** 没给 `--go` 开起来，后面每条
    都只打计划、不动臂（想真动得退出重开加 `--go`）；反过来也一样，开起来就每条
    都要按一次回车确认。参数同理 —— 只在命令行给一次，要改就退出重开。
    `Ctrl-C` 会终止整场（中途停臂必须能停）；想只退这一条指令，打 `quit`。
